# Localization

1. **No hardcoded user-facing text** — visible text, `aria-label`, `title`, `alt`, `placeholder`, toast/notification text, page titles all go through i18n.
2. Templates use `$t("key")`; `<script setup>` uses `const { t } = useI18n()`. Both are the project idiom. No custom translate wrappers, no `getCurrentInstance()?.appContext.config.globalProperties.$t`.
3. Interpolation via params: `t("key", { name })`. Never concatenate translated fragments or build sentences in code; for markup inside a sentence use `<i18n-t>`. Plurals via vue-i18n plural syntax, not `count === 1 ? ... : ...`.
4. A new key is added to **all 13** locale files of the same scope: `en ru de es fi fr it ja no pl pt sv zh`. English text is an acceptable fallback in other locales. Removed keys are removed from all 13. CI runs `yarn check-locales`.
5. Scope: global `locales/*.json`, UI kit `client-app/ui-kit/locales/*.json`, module `client-app/modules/<m>/locales/*.json`. Module strings live in the module's locales.
6. Keys: dot notation with snake_case segments (`shared.catalog.product_card.price_label`). Don't build key names dynamically unless every possible key exists (and prefer an explicit `Record<Union, key>` map).
7. Translations must be in the right language and fit the UI: no gendered first-person phrasing for messages
   any user can trigger (prefer neutral forms), counts via plural syntax or with the number placed so the
   sentence stays grammatical (`"Points balance: {n}"`).
8. Display values coming from the backend with a code (roles, statuses) are mapped through a key with a fallback
   (`t("common.roles." + id, name)`) consistently everywhere they are shown.
9. Dates via `$d` / `d`, numbers via `$n` / `n` (formats in `i18n.ts`), money via UI-kit price components — never format locale-sensitive values by hand.
